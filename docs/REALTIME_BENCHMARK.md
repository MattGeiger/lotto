# Realtime public-delivery benchmark

## Purpose

`npm run realtime:benchmark` runs a bounded synthetic A/B experiment against
the isolated realtime hub. An equal-sized polling cohort and WebSocket cohort
observe the same checksummed revisions in the dedicated
`william-temple-house-benchmark-e2e` Durable Object.

The runner measures:

- publish-to-observation p50, p95, p99, and maximum latency for both cohorts;
- WebSocket connection latency;
- complete delivery and checksum agreement for every client/revision pair;
- snapshot requests generated by the polling cohort;
- recurring snapshot requests generated by the healthy realtime cohort; and
- projected hourly polling reads at the configured synthetic cadence.

Each run writes a timestamped JSON report under
`artifacts/realtime-benchmarks/`. That directory is intentionally ignored by
Git so repeated measurements do not enter source control by accident.

## Scope and claims

This is a Phase 2 transport experiment. It uses synthetic state stored directly
in the Durable Object. It does not call the Vercel application, authenticate a
staff user, read Neon, or alter the beta LOTTO queue.

A passing report proves that the two delivery mechanisms observed the same
synthetic revisions and quantifies their latency and recurring-read difference.
It does **not** yet prove lower Neon compute. That claim requires Phase 3 shadow
publication from committed Neon state, Phase 4 client integration, and bounded
Neon/Vercel/Cloudflare platform measurements around the same workload window.

## Safety boundaries

The runner:

- uses only `william-temple-house-benchmark-e2e`;
- caps each cohort at 100 clients and each run at 20 measured publications;
- caps runtime at ten minutes;
- accepts local `localhost` or `127.0.0.1` targets without a remote override;
- requires `REALTIME_TEST_ALLOW_REMOTE=beta` for a remote run;
- requires the remote hostname to exactly match the expected beta hostname;
- requires HTTPS remotely; and
- never prints or writes the publish token.

The default remote hostname is
`lotto-realtime-beta.et2-geiger.workers.dev`. A future custom beta hostname must
be named explicitly with `REALTIME_TEST_EXPECTED_REMOTE_HOST`. Do not point the
runner at `williamtemple.app` or any future production Worker.

## Local run

Configure the local Worker token in the gitignored
`workers/realtime-hub/.dev.vars`, then start the Worker:

```sh
cd /Users/russbook/Repos/lotto
npm run realtime:dev
```

In a second terminal, securely enter the same local token and run the protocol
verifier followed by the benchmark:

```sh
cd /Users/russbook/Repos/lotto
read -s "REALTIME_TEST_PUBLISH_TOKEN?Local publish token: "
export REALTIME_TEST_PUBLISH_TOKEN
npm run realtime:verify
npm run realtime:benchmark
unset REALTIME_TEST_PUBLISH_TOKEN
```

The defaults create 10 polling clients, 10 WebSocket clients, five measured
publications, and a one-second synthetic polling cadence. The short cadence is
for a fast functional comparison, not a claim about LOTTO's adaptive production
polling configuration.

## Remote beta run

Run only during a declared measurement window, using the Cloudflare beta
publish token through a secure local secret source:

```sh
cd /Users/russbook/Repos/lotto
export REALTIME_TEST_BASE_URL=https://lotto-realtime-beta.et2-geiger.workers.dev
export REALTIME_TEST_ALLOW_REMOTE=beta
export REALTIME_TEST_ORIGIN=https://beta.williamtemple.app
npm run realtime:benchmark
unset REALTIME_TEST_BASE_URL REALTIME_TEST_ALLOW_REMOTE REALTIME_TEST_ORIGIN
unset REALTIME_TEST_PUBLISH_TOKEN
```

Before the command, `REALTIME_TEST_PUBLISH_TOKEN` must already be exported from
a secure prompt or secret manager. Do not paste it into documentation, shell
history, screenshots, issue reports, or a committed environment file.

## Configuration

| Variable | Default | Bounds and purpose |
| --- | ---: | --- |
| `REALTIME_BENCHMARK_CLIENTS` | `10` | Clients per cohort, 1–100 |
| `REALTIME_BENCHMARK_PUBLICATIONS` | `5` | Measured revisions, 1–20 |
| `REALTIME_BENCHMARK_POLL_INTERVAL_MS` | `1000` | Synthetic polling cadence, 250–60,000 ms |
| `REALTIME_BENCHMARK_TIMEOUT_MS` | `max(15000, 2 × poll interval)` | Per-observation timeout, 1,000–120,000 ms |
| `REALTIME_BENCHMARK_IDLE_MS` | `0` | Optional realtime-only idle/wake probe, 0–300,000 ms |
| `REALTIME_BENCHMARK_MAX_DURATION_MS` | `120000` | Whole-run deadline, 10,000–600,000 ms |
| `REALTIME_BENCHMARK_REALTIME_P95_TARGET_MS` | `2000` | Automated realtime p95 gate, 50–30,000 ms |
| `REALTIME_BENCHMARK_OUTPUT_DIR` | `artifacts/realtime-benchmarks` | Timestamped report destination |

Configuration is rejected before any connection or publication when the
publication cadence plus idle window cannot fit inside the runtime cap.

## Automated gates

A run exits successfully only when:

- both cohorts observe every expected client/revision pair;
- every observed checksum matches the published checksum;
- aggregate realtime p95 is within the configured target; and
- the healthy realtime cohort performs no recurring snapshot reads.

The process exits nonzero when a gate fails, which allows the same runner to be
used later from a beta-only CI or scheduled experiment. The JSON report remains
the evidence; a single green run is not a production-readiness decision.

## Platform measurement window

For a remote evidence run, record the start and end timestamp and capture:

1. Cloudflare Worker requests, Durable Object requests, WebSocket messages,
   duration, errors, and storage operations.
2. Vercel `/api/state` requests and function invocations. They should remain
   unchanged during this Phase 2 runner because it bypasses Vercel.
3. Neon compute-active and suspended intervals. They should remain unchanged
   during this Phase 2 runner because it bypasses Neon.
4. The generated JSON report and its exact configuration.

Hibernation is a platform property, not something the runner can infer from a
fast delivery alone. When `REALTIME_BENCHMARK_IDLE_MS` is nonzero, the runner
uses a separate `william-temple-house-idle-e2e` object with WebSocket clients
but no polling cohort or snapshot reads during the idle window. That separation
avoids the false test in which polling the comparison object repeatedly wakes
it. Successful post-idle delivery is application evidence; Cloudflare metrics
must still confirm that the object actually hibernated. Browser fallback,
background/foreground behavior, and real iPadOS 15 compatibility remain
separate Phase 4/5 automation and physical-device gates.
