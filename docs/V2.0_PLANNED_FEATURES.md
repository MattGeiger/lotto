# v2.0 Planned Features

**Status:** Provisional architecture direction selected; proof of concept and
production validation required. The earlier application-feature scope largely
shipped in **v1.18.0** (2026-06-30), but v2.0 itself is not yet approved or cut.
**Release intent:** v2.0 major architecture upgrade
**Primary scope:** A Neon-authoritative, Cloudflare Durable Object realtime
public-state hub that replaces ordinary healthy-client polling with versioned
WebSocket delivery while preserving adaptive polling as automatic fallback.
**Primary gate to v2.0:** The multi-phase proof program in
`docs/V2.0_REALTIME_ARCHITECTURE_PLAN.md` must pass experimentation, isolated
prototype, beta-stack, shadow, canary, cost, security, failure-recovery, and
real-iPad validation. The direction remains provisional until those gates pass.
**Prior application scope:** Staff login + authenticated navigation, an
announcement builder, AI translation and expanded localization, ticket-status
revert, and the Pantry Time game candidate remain recorded below. Pantry Time
is no longer the sole v2.0 release gate; its concept/prototype work remains in
the v1.30 game-review track and may ship independently of the realtime
architecture.

> **Note on scope history:** the *original* v2.0 plan was the **Arcade track**
> (dedicated `/arcade`, NOW SERVING banner, Snake, retro visuals) plus the
> personalized homepage and `/display` board. That work **shipped** across
> v1.5–v1.16 and is recorded under

#### Feature 3b — Translation Management (resilience)

**What.** AI translation requests can **fail** or **stall in pending**. FEED
solves this with a Translation Management layer that **stores** every
translation, lets staff **correct** them, **retry** failed/stuck ones, and run a
**"Find Missing Translations"** audit. LOTTO must port this so localization is
trustworthy (Features 2 and 4 depend on it).

**Borrow (FEED) — backend.**
- `packages/backend/src/services/translation-auditor.ts` — **Find Missing
  Translations**: audits all content × enabled languages, reports gaps by
  type/language, and optionally creates + queues the missing ones (also used when
  a new language is enabled).
- `packages/backend/src/services/translation-recovery.ts` — detects and retries
  **stuck/pending** translations (one automatic recovery attempt per item).
- `packages/backend/src/routes/translations.ts` — endpoint behaviors to
  re-expose as Next route handlers: `POST /find-missing`, `POST /recover-stuck`,
  `POST /:id/retry`, `POST /bulk-retry`, `PUT /:id` (manual correction),
  `GET /metrics`, `GET /performance`, plus list/CRUD/bulk-delete.

**Borrow (FEED) — frontend.**
- `packages/frontend/src/components/translation-management/*` — the management
  UI: `index.tsx`, `TranslationList/`, `data-table/`, `edit-dialog.tsx` (manual
  correction), `retry-dialog.tsx`, `find-missing-dialog.tsx`,
  `enhanced-find-missing-dialog.tsx`, `add-dialog.tsx`, `delete-dialog.tsx`,
  `form/`, `utils/`, `types.ts`.

**Build (LOTTO).** A `translations` table in Neon keyed by (content key, language)
with a **status** (`pending` / `complete` / `failed`) and the translated text;
the AI calls from Feature 3 write through it (so a failure is recorded, not
lost). Port the auditor + recovery as `src/lib/ai/translation-auditor.ts` /
`translation-recovery.ts`, expose the routes above under
`src/app/api/translations/*`, and port the management UI into the `/admin`
Translation Management section. For LOTTO the "content" set is the UI string keys
(Feature 4) plus the active announcement (Feature 2).

**Effort/Deps.** Medium-Large; part of the Feature 3 workstream (build alongside
the AI stack). Directly de-risks Features 2 and 4.

### Feature 4 — Language settings & expanded localization

**What.** Reuse FEED's language settings + translation to go beyond LOTTO's eight
hardcoded languages. Hardcoded translations stay as-is; authenticated users can
**enable additional languages** (e.g. Bosnian). Enabling a language triggers AI
translation of all mapped UI strings; once complete, clients can select it
alongside the hardcoded options. With **>10** total languages, apply a
**scroll area** to language selection (onboarding modal **and** dropdown).

**Borrow (FEED).**
- `packages/frontend/src/config/language-config.ts` — the 59-language
  `SUPPORTED_LANGUAGES` list (and `DEFAULT_ACTIVE_LANGUAGES`).
- `packages/frontend/src/components/language-management/*` — enable/disable UI,
  `language-filter.tsx`, `language-deactivation-dialog.tsx`; FEED `LanguagePage`
  (route in `App.tsx`).
- `packages/backend/src/routes/languages.ts` — enabled-language persistence +
  the translation-trigger hook on enable.

**Build (LOTTO).** Today translations are a hardcoded map in
`src/contexts/language-context.tsx` (8 languages). Keep that as the base; add a
Neon-backed dynamic translation store for enabled languages, and make `t()` fall
back hardcoded → DB-translated → English. Enabling a language enumerates the
existing translation keys and AI-translates them (Feature 3) into the new
language. Add a `ScrollArea` to the switcher (`src/components/language-switcher.tsx`)
and the onboarding language step when options exceed 10. Reuse `src/lib/rtl-utils.ts`
and extend it for any new RTL languages.

**Effort/Deps.** Large. Depends on Feature 3.

**Status: ✅ Implemented (v1.18.0).** The client bridge completing the AI
translation stack. `t()` in `src/contexts/language-context.tsx` resolves
hand-authored → DB-translated pack → English → key; the provider lazily loads
the visitor language list and fetches `/api/translations/pack?code=<bcp47>`
(built by `src/lib/translation/pack.ts`) for any non-English language. A dynamic
language becomes client-visible only when every UI string and active
visitor-facing brand string has a completed translation (`isLanguageReady` /
`GET /api/languages?client`). Saving a newly enabled language automatically
runs the complete staged **Find Missing** sweep in Admin. The public endpoint
withholds incomplete languages, so Home, Display, onboarding, and Arcade consume
the same ready-only dynamic list with native labels and scroll past 10 options;
visitors never poll for translation readiness. The onboarding announcement and
public service label render their visitor-language translation with English
fallback. The `Language` type widened to catalog codes
(`CoreLanguage` remains the hardcoded eight): dates use BCP-47 + Intl, wait-time
phrasing falls back to English, FEED public-inventory names resolve by catalog
name, and Urdu joined the RTL set. Covered by `tests/translation-pack.test.ts`;
validated end-to-end in the browser (Bosnian: onboarding "Bosanski" option,
announcement + Continue ("Nastavi") + board ("Trenutno uslužujemo") all
localized). v1.22.3 extended the bridge to active custom service labels and
removed Arcade's obsolete private eight-language picker.
The Arcade picker refreshes the ready catalog on explicit menu open rather than
relying on a once-per-provider result, so staff activations become visible in a
long-lived client session without background polling.

### Feature 8 (provisional, gating) — Realtime public-state architecture

**What.** Replace ordinary healthy-client `/api/state` polling with versioned,
near-realtime public-state delivery through one Cloudflare Durable Object hub
per agency. Neon remains authoritative for authenticated state transactions,
snapshots, undo/redo, restore, auth, configuration, translations, and reporting.
The hub retains only an allowlisted public projection and broadcasts it over
hibernatable WebSockets. Adaptive polling remains the automatic degraded mode.

**Why v2.0.** This adds a second runtime, a cross-system publication protocol,
monotonic revision reconciliation, realtime connection state, new deployment
and security boundaries, and production recovery responsibilities. Those are
major architectural changes even if the visible queue workflow remains
familiar.

**Decision status.** Direction selected for proof, not accepted for production.
The current app remains the supported baseline until the experiment passes all
gates. A failed proof can return to tagged CDN delivery or the existing polling
architecture without migrating authoritative data.

**Production-shaped beta.** The full-stack prototype should run in a separate
Vercel project at `beta.williamtemple.app`, with a fresh beta Neon database,
separate Blob store, auth secret/tables, Cloudflare Worker environment, Durable
Object namespace, metrics, and secrets. Beta must never point at the production
database or Durable Object state. Code and protocol versions can be promoted;
beta data and secrets cannot.

**Plan.** See `docs/V2.0_REALTIME_ARCHITECTURE_PLAN.md` for the complete phased
program: baseline, protocol experiment, standalone Cloudflare proof, beta
shadow publication, dual-read comparison, realtime-source canary, 30-day
production validation, v2.0 hardening, and post-release observation.

**Release gate.** v2.0 requires measured realtime latency, 100% revision/checksum
convergence at validation checkpoints, safe recovery from injected failures,
automatic polling fallback, at least 95% fewer public-origin Neon reads,
acceptable projected Cloudflare cost, security review, deployment/rollback
runbooks, and production-bundle validation on the real iPadOS 15 device.

## Surface Material Tokens ("Glass" Design System)

**Status:** Planned (v2.0 design-system track)
**Motivation:** v1.7.x introduced translucent "glass" treatments (translucent
fill + backdrop blur) across the bottom nav, dropdowns, popovers, switchers, and
the `/new` dialog — applied surface-by-surface with ad-hoc Tailwind values
(`bg-card/[45%]`, `backdrop-blur-[6px]`, etc.; see `docs/UI_DESIGN.md` →
"Translucent Surface Materials"). The dialog exposed the limit of one-value-fits-all
glass: a `DialogContent` over the `bg-black/40` overlay is both blurred **and**
darkened, dragging down text contrast. The fix is to treat each surface class as
a *material* with several independent parameters (tint, alpha, blur, brightness,
saturation) tuned per surface and per theme — which ad-hoc utility classes
cannot express cleanly.

**Goal:** promote the per-surface material settings into discrete, theme-aware
**material tokens** in global CSS, consumed via a small set of `.material-*`
utility classes (or `data-material="…"`), replacing the ad-hoc inline values.

Sketch (illustrative, not final):

```css
:root {
  /* one token set per surface "material" */
  --glass-dialog-tint: var(--popover);
  --glass-dialog-alpha: 0.55;
  --glass-dialog-blur: 2px;
  --glass-dialog-brightness: 1.6;   /* lighten the darkened overlay (light mode) */
  --glass-dialog-saturate: 1.2;
  --glass-dialog-edge: 255 255 255; /* lit top-rim highlight color */
  --glass-dialog-edge-alpha: 0.5;
  /* shadow follows the project glow convention — reuse --base-shadow-color,
     do NOT hardcode a literal blue (see UI_DESIGN.md → Shadows) */
  /* …nav, dropdown, popover materials get their own sets… */
}
.dark {
  --glass-dialog-alpha: 0.5;
  --glass-dialog-brightness: 0.9;   /* dark mode biases the other way */
  --glass-dialog-edge-alpha: 0.12;
  /* dark shadow is a soft blue-teal GLOW (illuminate, not darken) */
}

.material-glass-dialog {
  background-color: hsl(var(--glass-dialog-tint) / var(--glass-dialog-alpha));
  backdrop-filter:
    blur(var(--glass-dialog-blur))
    brightness(var(--glass-dialog-brightness))
    saturate(var(--glass-dialog-saturate));
}
```

**In scope for this track:**

- A small material taxonomy (e.g. `nav`, `dialog`, `dropdown`, `popover`) with
  per-material token sets and light/dark overrides.
- `.material-*` utility classes (or a data-attribute) so components opt in by
  intent, not by hand-tuned values.
- Solve the dialog contrast problem with the "lighten + transparency + blur"
  stack (`backdrop-brightness` composed into `backdrop-filter`), scoped to the
  dialog material so other surfaces are unaffected.
- Include **edge-highlight** (lit top rim) and **soft ambient shadow** as
  material properties; the shadow must honor the dark-mode glow convention
  (soft blue-teal, reusing `--base-shadow-color`) rather than a black drop.
- Migrate the existing glassed surfaces off ad-hoc utilities onto the tokens.
- Honor `prefers-reduced-transparency` (and reduced-motion where relevant) by
  falling back to opaque tints.
- Keep the Arcade material separate (`--arcade-*`), per guardrails.

**Out of scope:** changing *which* surfaces are glassed (that stays a human
design judgement); restyling the Arcade pixel-art material.
